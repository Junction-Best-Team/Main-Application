# Operational logging

API, worker and CLI diagnostics use single-line JSON on stderr through Python
logging. No new service, database table or logging dependency is required.
`aimo serve` disables Uvicorn's raw access log; our request events use route
templates, never customer path values or query strings. HTTPX request chatter is
suppressed. Successful health probes and empty worker polls stay quiet.
Uvicorn exception tracebacks and database-pool warnings are sanitized too, so
these loggers cannot repeat raw exception messages after our safe events.

## Trace a failed chat

Every tool start, completion and failure is logged even when no progress callback
is installed. `agent.tool_failed` includes the allowlisted tool name, stable
`error_code`, sequence, duration and `turn_id`. Unknown tool names are withheld.
Validation failures additionally report schema field names and validation error
types, never submitted values or unknown field names. `agent.complete` records
`TOOL_ERROR_LIMIT` or `TOOL_ROUND_LIMIT` when the runner returns a fallback.

Follow a request into the worker with these correlation fields:

- `request_id`: generated by the API, returned as `X-Request-ID`. Incoming values
  are ignored. Request context crosses synchronous handlers and streaming replies.
- `chat.queued`: joins that request to `turn_id` and `conversation_id` after the
  queue transaction commits, including accepted duplicates and explicit retries.
- `worker.claimed` / `chat.execute.*`: adds `attempt_id` and worker attempt count.
  `worker.attempt_limit` records exhausted interrupted claims.
- `agent.*`, `tool.call.*`, `service.*`, provider and database events inherit the
  current turn and attempt. Tool operations include the tool name and model round.

For example, replace `TURN_UUID` below with a turn found in the request's queue event:

```sh
kubectl -n junction logs deployment/aimo-api --since=30m |
  jq -R 'fromjson? | select(.event == "chat.queued")'
kubectl -n junction logs deployment/aimo-worker --since=30m |
  jq -R 'fromjson? | select(.turn_id == "TURN_UUID")'
```

Events use UTC timestamps. `duration_ms` is elapsed wall time. A function's
`.completed` event means it returned; inspect `agent.complete.error_code`,
guardrail verdicts and purchasing outcomes before interpreting it as success.
These logs do not authorize purchases or replace immutable purchasing audit events.

## Other boundaries

- LLM, embedding, reranking and supplier requests: HTTP status, attempt, duration,
  transport failure class, retries and stable final failure codes. LLM results
  include finish reason and numeric token usage even when a truncated reply is
  rejected. Model/provider response bodies and tool arguments are never logged.
- Guardrails: boundary, mode, policy version, model, verdict, failure category and
  check probabilities. Screened text is never logged.
- Service calls: start/completion/failure for catalog, policy, recipes, memories,
  basket preparation, confirmation and receipt reads, without their arguments.
  Safe summaries include result counts, recipe revision/unresolved count and
  purchasing statuses, so a successful tool returning a blocked basket is visible.
- Database: pool exhaustion, transaction exception class/SQLSTATE and connections
  taking at least one second. No SQL, bindings or connection URLs.
- Catalog/recipe ingestion: operation boundaries and safe failure locations, in
  addition to the existing catalog-sync outcome JSON.
- Worker: startup configuration (model/backend/mode only), readiness transitions,
  claimed jobs, iteration failures and shutdown.

Unexpected errors retain exception class and bounded stack locations (filename,
function and line). Exception messages, chained error text, source lines and
locals are excluded because they can contain secrets or customer content. Logs
also omit message text, prompts, model reasoning, headers, cookies, credentials,
supplier records and memory contents.

Application logs use Kubernetes' existing retention. There is no centralized
collector in this change: use `kubectl logs --previous` after a container restart,
and collect logs before pod replacement if historical investigation is needed.

## Main chat model

New defaults select `gemini-4-carbon` through the native Google API, with
`LLM_REASONING_EFFORT=low`, `LLM_MAX_COMPLETION_TOKENS=8192` and
`LLM_TIMEOUT_SECONDS=45` bounds each chat-model request. The overall turn budget is
`LLM_TURN_TIMEOUT_SECONDS=180` (configurable up to 180 seconds), including tool
execution and semantic checks. This stays below the 240-second worker lease and
shutdown grace period, and the 270-second health freshness limit. Catalog reads
run in groups of up to four; supplier calls and plan/purchase mutations stay ordered.
Once recipe discovery runs, catalog tools wait for a published quantity plan.
Each model round receives the remaining time and current matching stage, so it
can save selections incrementally and finish instead of repeatedly searching.
Opaque reasoning/signature blocks are replayed unchanged between tool rounds
within the turn; they are neither persisted in chat messages nor logged.
Set `LLM_REASONING_EFFORT` to an empty string to omit that override for a different
provider. Decision 1 supplies semantic checks and relevance ranking; Embedding 2
supplies product/recipe vectors. See [Google cutover](google-models.md).

Explicit environment/Secret settings, Terraform `llm_model`, and the GitHub
`LLM_MODEL` variable override defaults. For an existing installation, set that
repository variable to `gemini-4-carbon` as part of its authorized
release, and reconcile private Terraform inputs and old index profiles. Existing production values
are not modified by opening this PR. No merge, rollout or Terraform apply is
performed here.
