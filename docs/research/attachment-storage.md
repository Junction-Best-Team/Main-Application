# Research: durable storage and upload primitives for chat Attachments

**Ticket:** [#183](https://github.com/Junction-Best-Team/Main-Application/issues/183) (map [#24](https://github.com/Junction-Best-Team/Main-Application/issues/24))  
**Scope:** What durable object/blob storage and multipart (or equivalent) upload primitives already exist for buyer-scoped Attachment bytes (`.png`/`.jpg`/`.jpeg`/`.xlsx`/`.pdf`, ≤10 MB/file, ≤3 per message), and what gaps a ship must fill. Prefer the existing stack. No product implementation in this note.  
**Base:** `origin/develop` at research time (`research/attachment-storage`).

## Verdict

There is **no buyer Attachment upload API and no object/blob store for buyer file bytes**. The only durable blob-ish path in product code is **recipe-illustration staging in PostgreSQL `bytea` plus a signed Cloudinary image upload**, both server-side and outbound for AI-generated images—not buyer uploads. Chat “Attach file” in the UI is an inert placeholder. Terraform provisions **no** Spaces/S3/MinIO bucket. A ship for Attachments must add authenticated upload + durable buyer-scoped storage + bind-on-send; reuse PostgreSQL (and optionally Cloudinary only for public image delivery) rather than inventing a second cloud object system for this size envelope.

## What already exists

### 1. Cloudinary signed image upload (worker → CDN)

`src/aimo/image_provider.py` implements `upload_image`: signed `POST` to Cloudinary’s **image** upload endpoint with multipart `files={"file": ...}` via httpx. Caps and types are illustration-only:

- `MAX_IMAGE_BYTES = 10 * 1024 * 1024`
- Accepts generated `image/png`, `image/jpeg`, `image/webp`
- `public_id` must match `aimo/recipe-illustrations/[a-f0-9]{32}`
- Delivery URL is constructed from verified identifiers under `https://res.cloudinary.com/.../image/upload/...`

## Auth / session constraints uploads must respect

Mutating chat routes already require:

1. **Session cookie** `aimo_session` → `auth.browser_identity` (active identity, role `approver`, unexpired session).
2. **CSRF** `x-csrf-token` + **Origin** must equal `public_base_url` via `auth.csrf_check` (same pattern as conversation create / send message / confirm).
3. **Buyer ownership** of conversations (`conversations.owned` / `buyer_id` filters).

Any Attachment upload or bind-on-send endpoint must use the same session + CSRF + origin checks and must bind rows to `identity["buyer_id"]` (and conversation/message ownership). Do not put `CLOUDINARY_URL` or long-lived storage credentials in the browser; if using Cloudinary for image delivery later, keep signing server-side (current recipe-image model).

CSP already allows `img-src` Cloudinary for illustrations (`src/aimo/api.py`); PDF/XLSX delivery would need a different, authenticated fetch path if bytes stay private.

## Gaps a ship (#184) must fill

| Gap | Evidence |
| --- | --- |
| Buyer upload API (multipart or equivalent) with allowlist + 10 MB + ≤3/message | No `UploadFile`; Attach control inert; `MessageRequest` text-only |
| Durable Attachment object for buyer bytes (png/jpg/jpeg/xlsx/pdf) | Only `recipe_image_jobs.image_bytes` for AI images; no Attachment table |
| Bind Attachment IDs to the user message on send | `enqueue` hashes/stores text (+ constraints) only |
| Private retrieval for agent ingest / optional UI | Cloudinary URLs are public/unguessable (`docs/recipe-images.md`); unsuitable for arbitrary buyer docs without policy change |
| Object storage in infra | No Spaces/S3 in Terraform; Postgres is the durable store already |

Out of scope for this research ticket (called out on #24 / #184): retention after conversation end, malware scanning, SSE byte vs reference shape, exact vision/extract libraries.

## Recommendation (prefer existing stack)

1. **Do not add DigitalOcean Spaces (or a second blob product) for v1.** Caps (≤3 × 10 MB) fit the proven Postgres `bytea` + `octet_length` pattern from migration 015.
2. **Add a buyer-scoped Attachment ledger** (new migration): metadata (buyer_id, conversation_id, content_type/extension allowlist, size, created_at, optional message/turn bind) + `bytea` (or equivalent) with ≤10 485 760 bytes; enforce ≤3 attachments per message at bind time.
3. **Add authenticated upload route(s)** on the FastAPI buyer API: session cookie + CSRF + origin; validate extension/MIME/size; return Attachment id(s). Prefer multipart upload to the API (new inbound primitive—none exists today). Optionally accept Attachment ids on `MessageRequest` / bind during `enqueue` so bytes attach on send.
4. **Keep Cloudinary for recipe illustrations only** unless product later wants public image CDN for buyer photos; do not stretch `image/upload` + public delivery to PDF/XLSX. Reusing the httpx multipart **client** pattern toward Cloudinary does not satisfy buyer upload.
5. Agent turn ingest (vision / PDF-XLSX extract) remains ship work on #184, reading buyer-scoped stored bytes after bind.
